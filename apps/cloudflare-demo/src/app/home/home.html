Streamed hydration for Angular

Don't make the whole page wait for its slowest part

A server-rendered Angular page is sent when all of it is ready, so one slow request holds everything back. This project sends the page straight away and streams the slow parts into it as they finish, in the same response. Angular hydrates each part as it lands.

A page is as fast as its slowest request

Take a product page. The product itself renders at once. Its reviews take a second to load, and its recommendations take three. Here is that page sent three ways.

All three finish at the same moment: streaming does not make a slow request faster. What changes is everything else. Sent out of order, the product is on screen after 0.1 seconds and the reviews after 1, where the other two leave the reader with a blank or half-empty page for 3. The browser also gets to start on the styles, fonts and scripts that much sooner.

Where the idea comes from

Out-of-order streaming is about fifteen years old. Each framework that has it arrived at it for the same reason.

  1. 2010

    Facebook, BigPipe

    The page is cut into “pagelets”. The server flushes each one as soon as it has it, and a script call puts it into its placeholder. The reason given: When the web server is busy generating a page, the browser is idle and wasting its cycles doing nothing. The result: BigPipe reduces user perceived latency by half in most browsers.

    BigPipe: Pipelining web pages for high performance

  2. 2014

    eBay, Marko

    A late fragment is written into a hidden element, and a script moves it to a placeholder with a matching id. Without streaming, the user will be staring at a blank screen for a large portion of the time; and streaming in order means a fragment that is ready early waits behind the ones above it.

    Async fragments: rediscovering progressive HTML rendering with Marko

  3. 2021

    React 18, and Next.js on top of it

    A <Suspense> boundary sends its fallback first, then its HTML with an inline script that swaps it in. React named the problem You have to fetch everything before you can show anything, and the fix: Unlike traditional HTML streaming, it doesn't have to happen in the top-down order. Next.js puts it this way: A single slow database query or API call can block the entire page.

    New Suspense SSR architecture in React 18 Next.js: Streaming

  4. Also

    SvelteKit and Qwik

    SvelteKit streams promises returned from a server load, for slow, non-essential data. Qwik has it as an experimental mode: Out-of-order streaming helps when one section of the page is slow, but the rest of the page is ready.

    SvelteKit: Loading data Qwik: Pending

  5. 2026

    The browser itself

    HTML is getting the mechanism built in: a <template for> that fills a <?marker> earlier in the document, with no script. Chrome's intent to ship targets version 150, and notes that these are primitives that have been part of userland libraries for about a decade. Chrome's own guide still calls it shipped in only a single browser engine, so this project moves the markup with a small inline script, as the libraries do.

    Intent to ship: Out of order streaming Chrome: Out-of-order HTML streaming

And Angular?

Angular renders a page on the server and sends it whole; its roadmap has no streaming on it. What it does have is incremental hydration: a @defer block with a hydrate trigger stays as plain server HTML until the trigger fires. Angular is not touching that markup yet, so the server can replace it underneath a running app. That is the piece this project builds on.

What it costs

  • The status code is sent first

    It goes out with the shell. A part that fails later cannot turn the response into an error page or a redirect.

  • Placeholders get replaced

    Content can shift when they are. Give each placeholder the room its content will need.

  • A late part needs JavaScript

    A script puts it in place. With scripts off, the reader keeps the placeholder.

  • No caching as it stands

    A cached copy of half a response is worse than none, so streamed pages are sent with Cache-Control: no-store.
